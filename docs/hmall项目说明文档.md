# hmall 枫叶商城 — 项目说明文档

> 本文档从工程全景视角，概括 hmall 的**项目背景**、建设过程中遇到的**核心问题**、对应的**解决方案**以及落地后的**最终效果**。
项目链接：https://github.com/promisestar/hmall
---

## 1. 项目背景

hmall（枫叶商城）是一套面向教学与工程实践的**生产级电商平台**，目标不是做一个「能跑通下单」的演示 Demo，而是同时覆盖：

- **C 端消费者**：浏览搜索、购物车、下单支付、限时秒杀、个性化推荐
- **B 端运营者**：商品/库存管理、订单运营、秒杀活动配置、RBAC 权限、AI 运营日报
- **AI 智能助手**：自然语言完成购物与管理操作，并具备用户画像与跨会话记忆能力

技术形态上采用「三端分离」：

| 端 | 技术栈 | 职责 |
|----|--------|------|
| 前端 | Vue 3 + TypeScript + Element Plus | `/portal` 消费者端 + `/admin` 管理端 |
| Java 微服务 | Spring Cloud Alibaba（Nacos / Gateway / Feign / Sentinel / Seata） | 高并发交易与业务数据闭环 |
| Agent 服务 | DeepAgents + LangGraph + Python | 双 Agent（Customer / Admin）对话编排与工具调用 |

基础设施包括 MySQL（按服务分库）、Redis（缓存 / 限流 / 画像）、RabbitMQ（异步削峰与最终一致性）、Elasticsearch（搜索与推荐召回）、LightRAG（知识库）。

整体诉求可以概括为：**在真实微服务约束下，把交易可靠性、秒杀高并发、权限隔离与 AI 可控性一起做完整。**

## 2. 遇到的核心问题

建设过程中，真正决定架构取舍的矛盾集中在四类：

### 2.1 秒杀：库存准确 vs 瞬时高并发

普通下单用数据库事务即可；秒杀则不同——库存可能只有几十上百件，但开抢瞬间请求量远超市面查询能力。若把「有没有资格」全部压到 MySQL 行锁上，连接池与锁等待会先于业务逻辑把系统打垮。同时还必须同时满足：**不超卖、不超购、失败请求快速失败**，不能让用户长时间卡在「排队中」却毫无结果。

### 2.2 微服务：跨库一致性 vs 系统解耦

下单链路会跨 trade / item / user 等多个独立数据库；下单成功后还要发 MQ 清理购物车。强一致方案有性能与耦合代价，纯最终一致又可能在关键资金/库存路径上留下不可接受窗口。需要按业务风险分层，而不是「一个事务方案打天下」。

### 2.3 Agent：智能编排 vs 可控安全

LLM 擅长多步推理，但存在天然风险：高频只读指令仍走完整 ReAct 会浪费时延与 Token；取消订单、清空购物车、秒杀下单等破坏性操作不能依赖模型「自觉」；Admin 与 Customer 工具集必须硬隔离。核心难点不是「让 Agent 能做什么」，而是「让 Agent 不能越权做什么」。

### 2.4 个性化：数据孤岛 vs 实时体验

用户行为散落在加购、下单、支付、对话意图等多个服务与会话中。若推荐时实时跨服务聚合，延迟可达数秒；若只有数值画像，又记不住「想买手机但预算 5000、先再看看」这类自然语言意图。Agent 需要同时解决**冷启动、跨语言共享、跨会话记忆**。

## 3. 解决方案（核心能力）

### 3.1 微服务分层：Gateway 统一入口 + 数据自治

- **hm-gateway** 作为唯一 HTTP 入口，负责 JWT 认证与滑动窗口限流，下游微服务专注业务。
- 各服务独立数据库，服务间通过 Feign（同步）与 RabbitMQ（异步）协作；Agent **不直连 MySQL**，一律经 Gateway 调业务 API，避免 Agent 理解各库表结构导致强耦合。
- C 端用户与 B 端管理员采用**双 JWT / 双密钥体系**，数据表与认证链路彻底隔离。

### 3.2 秒杀三层防线：Redis 预减 + MQ 削峰 + MySQL 兜底

```
请求 → Gateway 限流（挡重复刷新）
     → Redis Lua 原子预减（限购 + 库存一次性判定）
     → 拿到资格后发 MQ 异步建单
     → MySQL 行锁最终扣减 / 失败回补
```

资格判断前置到 Redis，数据库只处理「真正有资格」的流量；前端通过结果轮询感知成功/售罄，避免把瞬时洪峰直接打进交易库。

### 3.3 分布式一致性分层

| 场景 | 策略 | 说明 |
|------|------|------|
| 下单扣库存/扣余额等跨库强一致 | Seata AT | 关键资金与库存路径要求同步正确 |
| 下单成功后清购物车等跨 DB+MQ | 本地消息表 + 定时重发 | 与业务写同事务落库，最终投递 |
| 订单超时未支付 | RabbitMQ 延迟消息 | 到期自动取消并释放资源 |
| 秒杀活动级联删除清缓存 | DB 事务强一致 + Redis 尽力清除 | 优先保证关联数据正确 |

### 3.4 Agent 三级路由 + 中间件硬约束

```
用户消息
  ├─ L1 正则快捷路由：高频只读（日报、猜你喜欢、查购物车等）跳过 LLM
  ├─ L2 interrupt 二次确认：危险写操作必须用户显式确认后才能继续
  └─ L3 LLM ReAct：复杂多工具编排才进入模型推理
```

中间件顺序固化为：认证 → 权限裁剪工具可见性 → 正则短路 → RAG 增强 → Skills 规范。权限与确认是**框架级闸门**，不依赖提示词约束。

### 3.5 三层用户画像 / 记忆

| 层级 | 存储 | 解决什么 |
|------|------|----------|
| Layer 1 行为流 | Redis List | 最近行为可回溯 |
| Layer 2 聚合画像 | Redis Hash（Java/Python 共享 db=0） | 类目/品牌/价格偏好毫秒级读取 |
| Layer 3 语义记忆 | LangGraph Store（`save_memory` / `get_memories`） | 跨会话购物意图延续 |

后端在加购、支付成功等节点用 `HINCRBY` 增量写画像；Agent 优先读 Redis，未命中再降级实时聚合并回写。画像写入失败静默处理，**不阻塞交易主流程**。

### 3.6 RAG 知识库桥接

商城政策、运营规则等非结构化知识通过 LightRAG 入库，Agent 侧以 MCP Server 桥接为工具调用，与交易 API 工具并存：结构化操作走微服务，文档型问答走知识库。

## 4. 最终效果

落地后，平台在「交易可靠、秒杀抗压、AI 可用可控、体验可个性化」四个方向形成闭环：

1. **完整购物与运营闭环**  
   消费者可完成搜索 → 加购 → 下单 → 支付 → 秒杀；运营可配置商品、活动与权限，并借助 AdminAgent 查询数据、生成日报。

2. **秒杀在高并发下可控**  
   超卖与超购由 Lua 原子逻辑前置拦截；未抢到的请求可快速失败；抢到的请求异步落库，交易库压力显著低于「全量直打 MySQL」方案。

3. **一致性按风险分级落地**  
   资金/库存路径有强一致保障，异步副作用有本地消息表兜底，避免「有订单无库存」或「消息丢失导致购物车脏数据」等典型事故形态。

4. **Agent 既快又安全**  
   高频只读指令可亚秒级返回且几乎不消耗 Token；危险操作必须人工确认；Customer / Admin 工具集硬隔离，降低越权与误操作面。

5. **推荐与对话越用越懂用户**  
   结构化画像支撑「猜你喜欢」类召回；语义记忆支撑跨会话意图延续；冷启动用户可通过降级聚合平滑过渡到画像命中。
